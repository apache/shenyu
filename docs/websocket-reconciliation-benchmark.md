# WebSocket reconciliation: canonical snapshot reuse

This addresses [#7840](https://github.com/apache/shenyu/issues/7840). Only the
admin-side reconciliation processing changes; field projection, gateway-side
snapshot application and receive-side JSON conversion remain independent.

## Representation and compatibility

The canonical representation is the existing lexicographically sorted list of
row JSON strings from `GsonUtils`. Both the digest and outgoing message reuse
these strings. The alternative of retaining a JSON tree alongside each sorting
string increases retained representations even for unchanged cycles; retaining
strings alone also lets unchanged cycles avoid creating trees entirely.

The digest is still MD5 of the UTF-8 encoding of `String.join("\n", rows)`.
Updates feed each row and a single LF byte **between** rows to `MessageDigest`.
There is no trailing delimiter, and the empty snapshot retains MD5 of the empty
string. Ordering, duplicate rows, field changes, additions and deletions remain
significant exactly as before. No digest migration is needed.

For changed groups a Gson `JsonWriter` writes the `WebsocketData` envelope and
inserts each canonical string with `jsonValue`. Values are generated by Gson,
never accepted as unvalidated input. There is no intermediate whole-snapshot
digest string/byte array and no per-row parse/tree/second serialization. The
writer still buffers the final message, as required by the existing collector.
Envelope fields, escaping and row order are checked against the old encoding,
including Unicode, embedded JSON, quotes, newlines, nulls and duplicate rows.

Every cycle still loads authoritative service state. Active namespace selection,
master gating, opt-in scheduling and `REFRESH`/`fullSnapshot` semantics remain
unchanged. Empty snapshots are sent to clear stale gateway state. A cursor only
advances after the existing synchronous `push` call returns; this preserves the
current publication contract and does not introduce a gateway acknowledgement.
Load, row serialization, message writing and publication exceptions leave the
previous cursor intact so the next cycle retries.

## Reproduce the processing benchmark

`WebsocketDataReconcilerBenchmark` is an opt-in test fixture with no new
dependencies. It is outside normal Surefire test naming and additionally requires
`shenyu.reconciliation.benchmark=true`. It compares a frozen copy of the old
algorithm with the actual modified reconciler, using identical DTO shapes,
deterministically shuffled rows and an in-memory replacement for service loads
and publication. Scheduling is bypassed so a synchronous tick can be measured.

Run from the repository root (use `./mvnw.cmd` in PowerShell, quoting each `-D`
argument as shown):

```sh
./mvnw -pl shenyu-admin -am test \
  '-Dtest=WebsocketDataReconcilerBenchmark' \
  '-Dsurefire.failIfNoSpecifiedTests=false' \
  '-Dshenyu.reconciliation.benchmark=true' \
  '-Djacoco.skip=true' \
  '-DargLine=-Xms768m -Xmx768m -XX:StartFlightRecording=filename=target/reconciliation.jfr,settings=profile,dumponexit=true'
```

Defaults are 20 warmup ticks per implementation/workload, three samples of five
ticks, 1k/10k rows per PLUGIN/SELECTOR/RULE group and 256/4096-character
config/handle strings. Selectors and rules also have a URI condition. Other
groups are empty, so every tick still performs three service loads. Unchanged
ticks emit nothing; changed ticks mutate one row's name without publishing an
event, and must emit exactly one snapshot. The two implementations must produce
identical final messages and digest cursors after every sample.

Override positive `shenyu.benchmark.warmup`, `shenyu.benchmark.samples` and
`shenyu.benchmark.iterations` for longer runs. Sample order alternates baseline
and canonical implementations. Explicit GC runs **outside** each timed sample;
the DTO fixtures remain live for both implementations. CPU time and allocated
bytes come from the current reconciliation thread's JDK management counters.
Wall time covers the complete synchronous tick including the three service
loads. `peak_observed_heap_bytes` samples process heap use on a separate daemon
thread with a requested 1 ms delay, including observations at the sample
boundaries. It is an observed peak, not an exact maximum or live-set size; short
peaks between observations can be missed. Sampling allocations are excluded from
the reconciliation thread's allocation counter, but included in process heap/GC.
GC counts/times cover only the measured batch. Setup, assertions and CSV writing
are excluded from timing. On Windows, thread CPU accounting is quantized, so
short batches can report zero CPU time; use longer batches for precise CPU
comparisons of small snapshots.

Raw samples are written to
`shenyu-admin/target/websocket-reconciliation-benchmark.csv`; the recording is
`shenyu-admin/target/reconciliation.jfr`. Retain the CSV, JFR, JVM arguments and
host details for repeated runs. JFR spans both implementations, so use the
`LegacyReconciler.reconcileSafely` and `WebsocketDataReconciler.reconcileGroup`
stacks to distinguish them; thread counters supply exact per-sample allocation
totals. This fixture measures serialization/digest/payload processing. Its three
service calls per tick are **not measured database reads**; it does not measure
WebSocket transport, gateway convergence latency or business-request p99.

## Correctness checks

```sh
./mvnw -pl shenyu-admin,shenyu-sync-data-center/shenyu-sync-data-websocket -am test \
  '-Dtest=WebsocketDataReconcilerTest,WebsocketCollectorTest,ShenyuWebsocketClientTest,WebsocketDataHandlerTest' \
  '-Dsurefire.failIfNoSpecifiedTests=false' '-Djacoco.skip=true'
```

The admin regressions compare both digest and complete wire messages with the old
implementation and exercise changed order, unchanged polling, field changes,
insertions, deletions, empty snapshots, load/serialization/publication failures,
namespace isolation and master gating. Existing gateway regressions check
authoritative cache replacement, removal of missing rules, empty snapshot
clearing and preservation of other namespaces.

## Deployment measurements required for end-to-end claims

Follow [#7650](https://github.com/apache/shenyu/issues/7650) on the target
deployment, with identical database contents, JVM resources, gateway/upstream
versions, plugin configuration and load generator settings:

1. Run baseline and canonical builds with reconciliation enabled and the same
   interval, connected namespaces and master role. Also record a disabled control.
2. Seed 1k/10k+ rows for each group, with both handle sizes. Warm the JVM and run
   repeated unchanged cycles. Change rows directly in the shared database to
   exercise missed-event recovery; include insertions, field edits, partial
   deletion and deletion of the last row.
3. Collect admin CPU, allocation/JFR, GC, peak heap, actual SQL counts and complete
   tick duration. This optimization intentionally does not remove authoritative
   database reads. Measure each deployment's queries rather than equating service
   invocations to SQL statements.
4. At a fixed business arrival rate collect successful throughput, errors,
   p50/p95/p99 and synchronization convergence time. Include a direct-upstream
   capacity control and verify final gateway state after each change. Exercise
   publication failure/recovery and non-master/no-session controls.
5. Retain raw results for multiple fresh JVM runs, report ranges, and compare
   resource cost at equal successful throughput. Do not infer business latency
   or end-to-end improvements from the isolated processing results below.

## Local processing results

Environment: 2026-10-19, Windows 11 amd64, AMD Ryzen 9 8945HX (16 cores/32
logical processors), approximately 31.8 GiB RAM, Eclipse Temurin
21.0.10+7-LTS, G1, `-Xms768m -Xmx768m`, JFR `profile`, no CPU affinity or quota.
The checkout is based on `297ac6f84`; the baseline fixture freezes its original
reconciliation algorithm. Both variants run in each fresh JVM against identical
fixtures. This is a shared developer workstation, not an isolated throughput
test environment.

Across these shapes, changed-cycle median wall time decreases by 57.0–68.2%
and allocation decreases by 41.0–63.9%. Unchanged-cycle allocation decreases by
14.9–16.5%, but median wall time ranges from 13.4% slower to 27.0% faster;
small-case sample ranges overlap. There is no claim of a universal unchanged
latency improvement. For 10k/4096 changed groups, median thread CPU time is
326.56 → 128.12 ms (PLUGIN/RULE) and 350.00 → 131.25 ms (SELECTOR).

Across the 72 measured batches per variant/state, observed process heap peaks
are at most 761.5 → 565.0 MiB for unchanged workloads and 766.3 → 763.6 MiB for
changed workloads. Changed workloads can still approach the configured heap
limit; reduced allocation does not guarantee a proportionately lower peak.
Measured-batch GC counts total 183 → 58 (unchanged) and 519 → 328 (changed),
with collection times 256 → 71 ms and 1459 → 485 ms respectively. These sums
exclude explicit pre-sample GC and warmup, and are specific to this workload
mix and G1 configuration.

All 288 measured batches pass identical message/digest assertions and the
expected three service loads per tick, zero unchanged publications and one
changed publication. The separate regression run passes 108 admin/gateway tests,
including actual gateway cache replacement and namespace-preserving deletion.
Checkstyle and Apache RAT checks also pass for the admin and WebSocket sync
modules.

Before PR submission, the change was also applied to upstream `de93952d9` and
129 admin/gateway regression tests passed, including the newer master-redirect
tests. The reconciler and DTO source used by the processing benchmark are
unchanged between the recorded benchmark base and this submission base.

The retained JFR recordings are local build outputs
`shenyu-admin/target/reconciliation-run-1.jfr` and
`shenyu-admin/target/reconciliation-run-2.jfr`.

Database reads, WebSocket transport, full gateway convergence latency and
business p99 were not measured locally. The processing results establish a
benefit for this stage; deployment acceptance still requires the procedure above.
